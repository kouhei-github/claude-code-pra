# 単元11 定期実行の自動化（週次ダイジェスト）

|  |  |
|---|---|
| Cowork のユースケース | スケジュールタスクで、週次ダイジェストなどを決まった時刻に届ける |
| Claude Code での対応 | 週次ダイジェストを非対話モード（`claude -p`）で回し、cron / GitHub Actions に載せる |
| 所要時間 | 45分 |
| 使う機能 | `claude -p`（ヘッドレス実行）/ Skill / cron / GitHub Actions / フック |

## この単元でやること

週次ダイジェストを、まず**手で1回作って合格させて**から自動化します。動かないものを自動化しても意味がないからです。
次にそれを Skill に固め、`claude -p`（非対話）で完走するよう書き直します。
非対話では途中で確認を求めた時点で止まるので、「質問しない」「不明時はこう書く」を明示する必要があります。
最後に cron と GitHub Actions の両方に載せ、**失敗したときに誰がどう気づくか**まで設計します。

| | |
|---|---|
| 入力 | 週次/（W35・W36 のチケット・パイプライン・デプロイログ）＋ 先週のダイジェスト_2026-W35.md ＋ フォーマット.md |
| 出力 | `output/週次ダイジェスト_2026-W36.md` ＋ `output/skills/weekly-digest/SKILL.md` ＋ `output/run_weekly_digest.sh` ＋ `.github/workflows/weekly-digest.yml` ＋ `output/運用メモ.md` |
| 中心にある判断 | 人が見ていない状態で完走すること。そして失敗が誰にも気づかれない状態を作らないこと |

## 成功の定義

> **しきい値判定が機械的に行われ、先週の宿題2件が追跡され、失敗時に終了コード1で落ちて人に気づかれる仕組みがあること。**

次が満たせていれば合格です。細かい確認項目は末尾の「合格チェック」にあります。

- 4指標すべてが 🔴 判定になっている（フォーマットのしきい値どおり）
- 初回応答時間が**中央値**で計算されている（平均ではない）
- 「先週の宿題」2件それぞれに現状が書かれている
- `run_weekly_digest.sh` が失敗時に終了コード1を返す
- Actions ワークフローが PR を作る（main へ直接 push しない）
- 認証情報がファイルに直書きされていない

## 学習目標

1. **人が見ていない状態で走らせる**ための書き方を身につける（確認を求めない、失敗を検知する）。
2. 前週との差分を扱う。「先週の宿題」を追跡させる。
3. 自動化してよい仕事と、してはいけない仕事の線引きをする。

## Cowork との対応

| Cowork | Claude Code |
|---|---|
| スケジュールタスク | cron / GitHub Actions / launchd から `claude -p` を呼ぶ |
| 実行結果の通知 | 出力をファイルに書く、Slack Webhook に投げる、PR を作る |
| タスクの中身 | Skill（`.claude/skills/`）に手順を固定する |

## 素材

```
data/
  ダイジェスト_フォーマット.md          章構成・判定しきい値・禁止事項
  先週のダイジェスト_2026-W35.md        前週の完成品（「先週の宿題」の追跡元）
  週次/
    support_tickets_2026-W35.csv        前週: 平常運転
    pipeline_2026-W35.csv
    deploy_log_2026-W35.txt
    support_tickets_2026-W36.csv        今週: 悪化している
    pipeline_2026-W36.csv
    deploy_log_2026-W36.txt
```

W35 と W36 の間で、次が変化している。ダイジェストはこれを拾えなければならない。

| 指標 | W35 | W36 | 判定 |
|---|---|---|---|
| 新規受注額 | 約 9,600,000円 | 約 4,800,000円 | 🟢 → 🔴 |
| 初回応答時間（中央値） | 約 5.0時間 | 約 9.4時間 | 🟡 → 🔴 |
| 未解決P1 | 1件 | 3件 | 🟡 → 🔴 |
| デプロイ失敗 | 0件 | 2件 | 🟢 → 🔴 |

さらに、W35 のダイジェストには宿題が2件書かれている（API連携の問い合わせ増、カワセミ電機のP1）。
これが W36 でどうなったかを追跡させる。

## 手順

### Step 1 — 手で1回作る（15分）

自動化の前に、**手で1回作って合格させる**。動かないものを自動化しても意味がない。

### Step 2 — 非対話モードで動かす（10分）

`claude -p` は対話がない。つまり **途中で確認を求められたら止まる**。
確認が発生しない書き方に直す必要がある。

### Step 3 — スケジュールに載せる（15分）

### Step 4 — 失敗したときにどうなるか決める（5分）

## つまずきポイント

- **対話前提のプロンプトを cron に載せる**
  → 確認待ちで永久に止まる。「質問しない」「不明時はこう書く」を明示する。
- **平均と中央値を取り違える**
  → 応答時間は外れ値が効くので中央値。書式に指定があるなら従わせる。
- **失敗が誰にも気づかれない**
  → 終了コード・ログ・通知を設計する。自動化の本体はここ。
- **生成物を直接 main に push する**
  → レビューなしで成果物が入る。PR にすれば人が見る機会が残る。

## 自動化してよい仕事・いけない仕事

| 自動化してよい | 自動化してはいけない |
|---|---|
| 決まったデータを決まった形にまとめる | 顧客に直接届く文章の最終送信 |
| しきい値との比較で判定する | 「送るか送らないか」の判断（単元08の解約リスク高） |
| 前週との差分を出す | 人事評価・与信・解約可否など、人が責任を持つ判断 |
| 異常を検知して人に知らせる | 検知した異常への対処そのもの |

## 発展課題

`.claude/hooks/` を使って、ダイジェスト生成後に自動で禁止語チェックを走らせる。
生成 → 検証 → 通知、までを1本にすると、人は例外だけ見ればよくなる。
