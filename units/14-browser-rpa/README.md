# 単元14 業務まるごと RPA — 受注登録 → 承認 → レポート取得

|  |  |
|---|---|
| Cowork のユースケース | 繰り返しのブラウザ作業をまとめて片付ける／定期実行に載せる |
| Claude Code での対応 | CSV 10件を画面から登録し、別アカウントで承認し、レポートを取得するまでを自動化する |
| 所要時間 | 60分 |
| 使う機能 | Playwright（MCP / スクリプト）/ 環境変数によるシークレット管理 / cron・GitHub Actions |

## 学習目標

1. 人が見ていない状態で完走する RPA を書く（確認を求めない、失敗しても止まらない）。
2. **失敗する入力が混ざっている**前提で設計する。1件の失敗で全部を止めない。
3. 「不可逆な操作」を自動化するときの歯止め（冪等性・件数確認・実行ログ）を設計する。

## 前提

単元13を終えていること。練習台を起動しておきます。

```bash
cd apps/rpa-lab && npm run dev      # → http://localhost:4321
```

練習用アカウントのパスワードは既定で `demo` です。
`RPA_SALES_PASSWORD` / `RPA_APPROVER_PASSWORD` を設定すると、
練習台側と RPA 側の両方がその値を使います。

## 素材

```
data/
  受注登録キュー.csv      10行。うち3行はわざと失敗する
solution/
  rpa_flow.py             模範解答（自分で書いてから開く）
```

`受注登録キュー.csv` の中身：

| 列 | 内容 |
|---|---|
| 顧客名 | 顧客マスタの正式名称 |
| 営業担当 | 空欄ならログインユーザー |
| 明細 | `P-002x2;P-102x10` の形式（商品コード x 数量、`;` 区切り） |
| 納期 | `YYYY-MM-DD` |
| 備考 | 任意 |

**わざと失敗する3行**（ここが本題です）:

| 行 | 何が起きるか | 期待する挙動 |
|---|---|---|
| `存在しない株式会社` | 顧客の選択肢に無い | 「顧客マスタに存在しません」と記録して次へ |
| `株式会社ハルカゼ運輸` / `P-999` | 商品コードが無い | 「商品マスタに存在しません」と記録して次へ |
| `株式会社アカツキ食品` / 納期 `2026-01-10` | 過去日でバリデーションに弾かれる | 画面のエラー文を拾って記録し、次へ |

素直に書くと、この3行でスクリプトは 30 秒待たされたうえに
`Timeout 30000ms exceeded` としか報告しません。**それでは業務では使えません。**
「顧客マスタに存在しないので登録できませんでした」と返るのが正解です。

## 業務フロー

```
① 営業アカウントでログイン
      ↓
② CSV を1行ずつ、4ステップのウィザードで登録（→ 申請中になる）
      ↓  失敗した行は理由を記録して次へ
③ 承認者アカウントでログインし直す
      ↓
④ 登録できた受注を承認一覧から探して承認
      ↓  一覧はページ送りされる
⑤ 月次レポートを生成（3.5秒の非同期ジョブ）してCSVをダウンロード
      ↓
⑥ 実行ログ・サマリを出力
```

## 手順

### Step 1 — 手で1件だけ通す（15分）

自動化の前に、Claude に**画面を操作させて1件だけ**登録させます。
ここで「どこで待つ必要があるか」を洗い出します。単元13の `セレクタ設計.md` が効きます。

### Step 2 — スクリプトにする（20分）

対話で操作させるのと、スクリプトを書かせるのは別の仕事です。
定期実行するならスクリプトが要ります。

### Step 3 — わざと失敗する3行を潰す（15分）

1回目の実行では、失敗3行が Playwright の生のエラーで落ちます。ここを直します。

### Step 4 — 定期実行に載せる（10分）

## そのまま使えるプロンプト

**（A）まず1件を手で通す**

```
http://localhost:4321 の受注管理システムに、受注を1件登録してください。

【認証】営業アカウント。パスワードは私が入力します（あるいは環境変数
        RPA_SALES_PASSWORD から読んでください）。
【登録内容】@units/14-browser-rpa/data/受注登録キュー.csv の1行目

【やること】
1. ログインし、お知らせモーダルが出たら閉じる
2. /order-new の4ステップウィザードを最後まで進める
3. 登録された受注番号を報告する

【報告してほしいこと】
各ステップで「何を待つ必要があったか」を、待機条件つきで列挙してください。
（例: 顧客の select は空で描画されるので option が2つ以上になるまで待つ）

【制約】
- API を直接叩かない。画面を操作する
- 登録は1件だけ。CSVの残りには手を付けない
```

**（B）スクリプトにする**

```
(A) で分かった待機条件を反映して、Python + Playwright のスクリプトを書いてください。

【出力】units/14-browser-rpa/output/rpa_flow.py

【処理】
1. 営業アカウントでログイン（お知らせモーダルが出たら閉じる。出ないこともある）
2. data/受注登録キュー.csv を1行ずつ、/order-new のウィザードで登録
3. 承認者アカウントでログインし直し、登録できた受注を /approvals から探して承認
   ※ 承認一覧はページ送りされる。対象が見つかるまでページを辿る
4. /reports で 2026-09 のレポートを生成し、CSV をダウンロード
5. 結果を出力

【出力ファイル】
- output/実行ログ.csv    : CSVの全列 + 受注番号 + 結果 + エラー（1行1件）
- output/実行サマリ.json : 実行時刻 / 件数 / 承認済 / 失敗 / レポートのパス
- output/受注明細_2026-09.csv

【必ず守ること】
- 認証情報をコードに書かない。環境変数から読む
  （RPA_SALES_EMAIL / RPA_SALES_PASSWORD / RPA_APPROVER_EMAIL / RPA_APPROVER_PASSWORD）
- 待機に time.sleep を使わない。条件待ち（wait_for / expect）を使う
- 1件の失敗で全体を止めない。記録して次の行へ進む
- 人間への確認を求めない。判断が必要なら「要確認」と記録して先へ進む
- 途中でセッションが切れたら再ログインしてから続ける
- --headed オプションでブラウザを表示して実行できるようにする
```

**（C）失敗3行を業務の言葉にする**

```
units/14-browser-rpa/output/rpa_flow.py を実行すると、CSVの8〜10行目が
Playwright の Timeout エラーで落ちます。これを直してください。

【直し方の方針】
- 顧客が選択肢に無い場合: select_option を呼ぶ前に選択肢を読み、
  無ければ「顧客マスタに存在しません: <顧客名>」で即座に失敗させる
- 商品コードが候補に出ない場合: 短いタイムアウトで検知し、モーダルを閉じてから
  「商品マスタに存在しません: <コード>」で失敗させる
- 納期が過去日の場合: 次のステップに進めなかったことを検知し、
  画面のエラー文（#err-due）をそのままエラーメッセージに含める

【制約】
- タイムアウトを待たずに検知すること。3行の処理に30秒以上かけない
- エラーメッセージは、業務担当者が読んで何をすればいいか分かる日本語にする
- 直したあと、成功7件・失敗3件で完走することを確認する
```

**（D）定期実行に載せる**

```
このRPAを毎営業日の朝8時に自動実行する仕組みを作ってください。

【出力1】units/14-browser-rpa/output/run_rpa.sh
  - 環境変数が未設定なら、何が足りないかを表示して終了コード1で終わる
  - rpa_flow.py を実行し、終了コードを引き継ぐ
  - 実行ログを output/logs/YYYY-MM-DD.log に残す

【出力2】units/14-browser-rpa/output/運用メモ.md
  - crontab の設定行
  - 認証情報の置き場所（何を使い、何を使ってはいけないか）
  - 失敗したときに誰がどう気づくか
  - この自動化を止めるべき条件
  - 「二重登録」が起きうる場面と、その防ぎ方

【制約】
- 認証情報をファイルに書かない
- 実行前に「今日はもう実行済みでないか」を確認する仕組みを入れる
```

## 合格チェック

- [ ] 成功7件・失敗3件で**完走する**（途中で止まらない）
- [ ] 失敗3件のエラーが、業務担当者が読んで分かる日本語になっている
- [ ] 失敗3件の検知に、合計30秒以上かかっていない
- [ ] `time.sleep` による固定待ちを使っていない
- [ ] 認証情報がスクリプトにもログにも出てこない（`grep -ri password output/` で確認）
- [ ] 承認一覧のページ送りを辿れている（金額順で後ろのページにある受注も承認できる）
- [ ] レポートのポーリングが実装されている（押した直後にダウンロードしていない）
- [ ] `実行ログ.csv` を見れば、どの行がなぜ失敗したかが分かる
- [ ] 2回続けて実行しても、同じ受注が二重登録されない仕組みがある（または運用メモに書いてある）

## つまずきポイント

実際にこの練習台で起きたものだけを挙げます。

- **一覧が「0件」と判定される**
  ロード中のスケルトン行を掴んでいます。`tr` ではなく
  `tr[data-order-id], [data-testid=no-pending]` のどちらかを待ちます。

- **顧客が1件も選べない**
  `<select>` は空で描画され、あとから API 経由で選択肢が入ります。
  要素の存在ではなく `option` が2つ以上になったことを待ちます。

- **登録成功したのに「失敗」と判定される**
  トーストは明細追加のたびに出て5秒残ります。「最初のトースト」を読むと
  1つ前の操作の結果を掴みます。成功判定は**URLの遷移**を条件にするのが確実です。

- **「次へ」を押した直後に読んで、前のページの内容を読む**
  ページ番号表示が変わるのを待ってから読みます。

- **失敗3行で30秒ずつ待たされる**
  「やってみて落ちる」ではなく「やる前に確認して落とす」。
  選択肢を先に読む、短いタイムアウトで検知する。

- **エラーが `Timeout 30000ms exceeded` としか出ない**
  それを渡された担当者は何もできません。業務の言葉に翻訳するのは RPA 側の仕事です。

## 自動化してよいこと・いけないこと

この単元では**承認まで自動化しています**。実務でこれをやってよいかは別問題です。

| 自動化してよい | 人が判断すべき |
|---|---|
| CSV の内容をフォームに転記する | その受注を出してよいかの判断 |
| 一覧を辿って抽出する | 承認するかどうか |
| レポートを生成してダウンロードする | 差戻しの理由を書くこと |
| 失敗を検知して記録する | 失敗した案件をどう扱うか |

**承認を自動化するなら、「誰が責任を持つか」を先に決めてください。**
「RPAが承認しました」は組織の説明として成立しません。
実務では、承認は人が押し、RPA は「承認待ち一覧を整理して根拠を添える」までにする、
という切り方をよく使います。

不可逆な操作を自動化するときの最低限の歯止め：

1. **件数を先に確認する** — 「10件処理します」と宣言してから始める
2. **冪等にする** — 2回動いても二重にならない（登録前に既存を確認する）
3. **実行ログを残す** — 何を、いつ、どのアカウントで実行したか
4. **ドライラン** — `--dry-run` で「何をするか」だけ出力できるようにする

## 単元11との接続

単元11で作った週次ダイジェストは「読むだけ」の自動化でした。この単元は
**書き込む**自動化です。失敗したときの影響がまったく違います。

- 単元11の失敗 → レポートが出ない。人が気づいて手で作る
- 単元14の失敗 → **間違ったデータが業務システムに入る**。取り消しが要る

だから単元14では、実行ログと冪等性が単元11以上に重要になります。

## 発展課題

`--dry-run` を実装する。CSV を読んで検証だけ行い、
「登録可能7件 / 登録不可3件（理由つき）」を出力して終わる。
これがあると、朝いちの本番実行の前に安全確認ができます。
