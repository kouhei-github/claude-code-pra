# 単元12 総合演習 — サブエージェントで3社分のQBR資料を並列生成する

|  |  |
|---|---|
| Cowork のユースケース | 複数の成果物をまとめて作り、チームに出せる品質に仕上げる |
| Claude Code での対応 | 顧客3社 × 3成果物 = 9ファイルをサブエージェントで並列生成し、レビューまで回す |
| 所要時間 | 60分 |
| 使う機能 | サブエージェント（Task）/ `pptx` `xlsx` スキル / 自己レビュー / これまでの全単元 |

## 学習目標

1. 独立した作業を **並列に分割**する判断ができる（分割してよい仕事の見分け方）。
2. 顧客向け成果物と社内向け成果物の **情報の出し分け**を確実にする。
3. 生成物を **別のエージェントにレビューさせる**（作った本人にチェックさせない）。

## 素材

```
data/
  QBR資料の要件.md       成果物3点セット・守るべき5条件・レビュー観点5つ
  契約サマリ.xlsx        3社の契約情報（プラン/ライセンス/年額/利用状況スコア）
  ミナト製作所/          利用状況_直近12週.csv / サポート履歴_Q3.csv / 前回QBR議事録_2026-06.md
  九重ホールディングス/   同上
  ハルカゼ運輸/          同上
```

### 3社の状況（意図的に違えてある）

|---|---|---|---|

## 手順

### Step 1 — 分割できるか判断する（10分）

並列化してよいのは、**互いに依存しない**作業だけ。この演習では：

- 顧客A・B・Cの資料生成は互いに独立 → 並列にできる
- 3社を横断する社内サマリ → 3社が終わってから → 並列にできない
- レビュー → 生成が終わってから → 並列にできない

### Step 2 — 1社だけ手で作る（15分）

**いきなり3社を並列で走らせない。** まず1社（ミナト製作所）を作り、品質基準を固定する。

### Step 3 — 残り2社を並列で走らせる（15分）

### Step 4 — 別エージェントにレビューさせる（15分）

作った本人はミスに気づきにくい。**レビュー専用のサブエージェント**を立てる。

### Step 5 — 横断サマリ（5分）

## そのまま使えるプロンプト

**（A）1社目で基準を作る**

```
@units/12-subagents-capstone/data/QBR資料の要件.md に従って、
ミナト製作所の QBR 資料3点セットを作ってください。

【入力】@units/12-subagents-capstone/data/ミナト製作所/ の全ファイル
        @units/12-subagents-capstone/data/契約サマリ.xlsx

【出力】units/12-subagents-capstone/output/ミナト製作所/
  QBR_2026Q3.pptx（6枚）/ 利用状況分析.xlsx / 社内申し送り.md

【制約】要件.md の「必ず守ること」5項目をすべて満たすこと。特に:
- 顧客に見せる pptx / xlsx に、他社名・解約リスク・社内の推測を書かない
- 前回QBRの宿題3件すべてについて、完了/未完了/確認中を書く
- 数字は data/ミナト製作所/*.csv から計算する
```

**（B）残り2社を並列生成**

```
ミナト製作所と同じ品質・同じ構成で、残り2社の QBR 資料を作ってください。
2社は互いに独立しているので、サブエージェントを2つ立てて並列で進めてください。

【サブエージェント1】九重ホールディングス
【サブエージェント2】ハルカゼ運輸

各エージェントへの指示に必ず含めること:
- @units/12-subagents-capstone/data/QBR資料の要件.md を読むこと
- 出力先は units/12-subagents-capstone/output/<顧客名>/
- units/12-subagents-capstone/output/ミナト製作所/ を構成の見本にすること
- 利用状況スコアが40未満の顧客にはアップセル提案を入れないこと
- 他の顧客のデータを参照しないこと（自社の担当顧客のディレクトリのみ読む）

【制約】
- サブエージェントに data/ 配下への書き込みをさせない
- 2社の生成が両方終わってから報告する
```

**（C）レビュー専用エージェント**

```
units/12-subagents-capstone/output/ の3社分の成果物を、レビュー専用のサブエージェントで
検査してください。生成を担当したエージェントとは別に立ててください。

【レビュー観点】@units/12-subagents-capstone/data/QBR資料の要件.md の「レビュー観点」5つ
【追加観点】
6. ハルカゼ運輸の顧客向け資料にアップセル提案が入っていないか
7. 顧客向け資料（pptx / xlsx）に他社名が出ていないか
8. 前回QBR議事録の宿題3件が、3社すべての資料で言及されているか
9. pptx が全社6枚になっているか
10. xlsx にグラフが1つ以上入っているか

【出力】units/12-subagents-capstone/output/レビュー結果.md
  観点 | 顧客 | PASS/FAIL | 根拠（該当ファイルと箇所）| 修正案

【制約】
- レビュアーは修正しない。指摘だけ出す
- 「問題なし」と書く場合も、何を確認した結果かを書く
- ファイルを実際に開いて確認する。推測で PASS を出さない
```

**（D）修正と横断サマリ**

```
@units/12-subagents-capstone/output/レビュー結果.md の FAIL をすべて修正してください。
修正後、再度レビューを走らせて全項目 PASS を確認してください。

そのうえで、3社を横断した社内サマリを作ってください。
【出力】units/12-subagents-capstone/output/QBR横断サマリ.md（40行以内）
  - 3社の更新見込み（金額と確度）
  - アップセルの芽（金額と根拠）
  - 解約リスク（顧客名・根拠となる数字・推奨アクション・担当）
  - 3社に共通して出ている課題（あれば）

【制約】
- これは社内向け。顧客に送らない前提で書く
- 数字はすべて各社の成果物から引く
```

## 合格チェック

- [ ] 9ファイルすべてが生成されている
- [ ] pptx が3社とも6枚
- [ ] xlsx にグラフが1つ以上
- [ ] **ハルカゼ運輸の顧客向け資料にアップセル提案がない**
- [ ] 顧客向け資料に他社名が1つも出ていない
- [ ] 前回QBRの宿題3件が、3社すべての資料で言及されている
- [ ] 解約リスクの記述が `社内申し送り.md` にだけあり、pptx には無い
- [ ] レビュー結果が全項目 PASS
- [ ] 横断サマリが40行以内

## つまずきポイント

- **依存関係のある作業を並列にする**
  → 横断サマリは3社の完了が前提。並列にすると空のファイルを読む。
- **サブエージェントに基準を渡し忘れる**
  → 「見本は output/ミナト製作所/」と明示する。渡さないと3社ばらばらの構成になる。
- **顧客向け資料に社内情報が漏れる**
  → これが実務で最も危険。レビュー観点に必ず入れ、機械的に検査する。
- **作った本人にレビューさせる**
  → 見落としが再生産される。別のエージェントを立てる。
- **並列にしたのに結局遅い**
  → 1社目で基準を固めてから並列にする。基準がないとやり直しが発生する。

## この演習で使っている単元

| 単元 | どこで使うか |
|---|---|
| 02 プロンプト設計 | サブエージェントへの指示は「他人への依頼」そのもの |
| 04 スプレッドシート | CSV の集計と xlsx 出力 |
| 06 文書統合 | 議事録・CSV・契約情報を1つの資料にまとめる |
| 07 分析 | 12週の推移と前四半期比 |
| 09 CLAUDE.md | 3社に共通する制約は CLAUDE.md に置いておくと指示が短くなる |
| 10 Skill | QBR生成を Skill 化すれば、次の四半期は1コマンド |

## 発展課題

この演習を Skill 化し、`data/` に顧客ディレクトリを1つ足すだけで
4社目のQBRが同じ品質で出る状態にする。そこまで来ると、
四半期ごとに数日かかっていた作業が、レビューだけの仕事になる。
